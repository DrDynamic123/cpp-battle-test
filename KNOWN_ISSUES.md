# Известные недостатки и сомнения по решению

1. Случайный выбор цели из ТЗ реализован как выбор первого подходящего юнита в порядке `spawnOrder`.
2. Способности юнитов определяются через `dynamic_cast` от `IUnit`. Это небольшая runtime-цена, зато `Core` не хранит и не расширяет список указателей на способности.
3. Занятость клетки задаётся через `IUnit::occupiesCell()`. Это оставлено в `Core`, потому что блокировка клетки является инвариантом `World`, а не отдельной игровой способностью. `World` оставляет у себя `occupied_`, потому что это быстрый индекс занятых клеток. Индекс поддерживается только внутри `World`: внешний код вызывает `relocateUnit`.
4. Если dist == 1 и целевая клетка занята, марш завершается без движения.
5. `setPosition()` остаётся низкоуровневым методом `IUnit`, поэтому игровой код должен двигать юнитов через `features::actions::moveUnit`. Там проверяется `IMovable::maxStepDistance()`, чтобы не превратить шаг в телепорт.
6. В `Action` описан `features::actions::healUnit`, как пример расширяемости действий.
7. Несколько команд к одному юниту. Новый target просто заменяет старый. Для каждой команды всё равно логируется MARCH_STARTED. Последний `MARCH` перезаписывает цель.
